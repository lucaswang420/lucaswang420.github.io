🐳 Docker 多阶段构建复用规范脚本模式

文档信息 | 难度: intermediate | 预计用时: 35分钟 | 创建: 2026-08-12

📖 概述

在 C++ 项目的 Docker 化过程中，一个常见陷阱是 Dockerfile 中手写 cmake 命令，与项目的规范构建脚本（CI 和本地使用的同一脚本）产生漂移。容器构建与 CI/本地构建走不同路径，导致”本地通过但容器失败”或反过来的问题。

本文档介绍一种 Docker 多阶段构建复用规范脚本模式：Dockerfile 的 builder 阶段直接调用项目的 scripts/backend/build.sh Release（而非手写 cmake 命令），确保容器构建与 CI/本地构建走完全相同的路径。配合 BuildKit 缓存挂载和静态链接运行时，实现高效且一致的容器构建。

  • 静态链接 C++ 运行时镜像的极简化

3.1 BuildKit 缓存挂载

BuildKit 缓存挂载的优势：

  • Conan 下载的依赖包缓存在 Docker 层之外的卷中
  • 每次构建不需要重新下载依赖（首次几百 MB → 后续几秒）
  • 不污染最终镜像（缓存卷不成为镜像层）

4. 最佳实践

4.1 Docker Compose 的 target 字段

单文件 Dockerfile 包含所有阶段，通过 target 字段选择构建终点。这比多个 Dockerfile 更易维护——所有阶段定义在一个文件中，共享基础层。

4.2 前端构建变量的空默认值

空默认值确保 SPA 在未提供变量时回退到代码内默认值，而非 undefined。Docker Compose 的 build.args 传入实际值。

5. 常见问题

Q: 为什么运行时镜像用 Ubuntu 而非 alpine？

A: C++ 静态链接的二进制仍然依赖系统的 libc（glibc）。Alpine 使用 musl libc，与 Ubuntu 的 glibc 不兼容。如果 builder 阶段用 Ubuntu（glibc）编译，运行时也必须用 glibc 系统。选择 ubuntu:22.04 确保 libc 兼容，且镜像只有约 30MB（apt install ca-certificates + curl 后约 50MB）。

Q: 为什么不用 distroless 作为运行时？

A: distroless 镜像没有 shell 和包管理器，难以调试。对于 C++ 项目，ubuntu:22.04 + ca-certificates + curl 已经足够精简（约 50MB），且支持 HEALTHCHECK 中的 curl 命令。如果安全要求极高，可以改用 gcr.io/distroless/cc 但需要调整健康检查方式。

Q: Conan 缓存挂载在 CI 中如何工作？

A: 在 GitHub Actions 中，BuildKit 缓存可以通过 actions/cache 或 BuildKit 的 cache-from/cache-to 导出。CI 中持久化 Conan 缓存可以将依赖安装时间从几分钟缩短到几秒。

📝 总结

关键要点:

  1. 复用规范构建脚本：Dockerfile builder 阶段调用 build.sh，不手写 cmake 命令
  2. BuildKit 缓存挂载：Conan 缓存持久化，大幅减少重建时间
  3. 静态链接 → 极简运行时：Conan 静态链接所有依赖，运行时只需 ca-certificates + curl
  4. 单文件多阶段：一个 Dockerfile 包含前后端所有阶段，用 target 选择构建终点

💡 提示: “复用规范脚本”是本模式的核心思想。任何构建路径的分歧（本地 vs CI vs 容器）都是潜在 bug 的来源。通过让所有构建路径调用同一个脚本，从源头消除分歧。
