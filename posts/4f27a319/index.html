🏗️ Repository + Strategy 模式 (C++)

文档信息 | 难度: advanced | 预计用时: 40分钟 | 创建: 2026-08-12

📖 概述

在需要支持多种存储后端（PostgreSQL、Redis、内存）的项目中，Repository 模式是隔离 Domain 层与存储实现的经典手段。但当不同后端的能力差异较大（如 PostgreSQL 支持事务但 Redis 不支持），简单的单一接口会导致两种问题：要么接口降级到最低能力（PostgreSQL 的事务能力被浪费），要么接口充斥可选方法（调用者不知道哪些方法在自己的后端上可用）。

本文档介绍一种 Repository 接口 + Strategy Bundle + 能力标志 的组合模式：用纯虚接口定义存储契约，用 Bundle 模式将一组 Repository 打包为可切换的存储策略，用能力标志（supportsTransactions()、supportsCas()）让测试套件和运行时代码知道当前后端的能力边界。

4. 常见问题

Q: 为什么用 Bundle 而不是单独注入每个 Repository？

A: Bundle 确保所有 Repository 使用同一个后端——不会出现 Token 用 PostgreSQL 但 Client 用 Redis的不一致配置。切换后端时只改 Bundle 类型，一行代码完成全量切换。

Q: 能力标志用虚函数还是模板参数？

A: 虚函数。模板参数（CRTP 或 policy-based design）会在编译期确定能力，但这意味着每种后端需要不同的二进制。虚函数允许运行时切换（如配置文件选择存储类型），且能力标志的调用频率低（主要在测试套件和初始化时），虚函数分派开销可忽略。

Q: 缓存装饰器为什么不用 C++ 模板？

A: 装饰器用运行时多态（unique_ptr<IClientRepository> delegate_）而非编译时多态（模板），因为缓存的添加/移除应该是运行时配置决定的。用模板会导致 CachedClientRepository<RedisClientRepository> 和 CachedClientRepository<PgClientRepository> 是不同类型，无法统一存储在 Bundle 中。

📝 总结

关键要点:

  1. 纯虚接口 + 异步回调：Domain 层定义存储契约，不依赖具体后端
  2. Strategy Bundle：一组 Repository 打包切换，配置一处改全部切
  3. 能力标志：supportsTransactions()/supportsCas() 驱动分层契约测试，不谎报
  4. 默认实现 + 覆写：接口提供非原子默认实现，支持事务的后端覆写为原子版本
  5. 缓存装饰器：用装饰器模式为 Repository 添加缓存层，不修改原始实现

💡 提示: 能力标志模式的核心价值不在于”跳过不支持的测试”——而在于让架构决策变得可测试。当你添加一个新后端时，能力标志会告诉你（和 CI）哪些契约测试应该通过，哪些可以跳过。这消除了”新后端忘记测试某个能力”的风险。
