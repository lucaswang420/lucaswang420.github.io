📝 日志规范与分层策略

文档信息 | 难度: intermediate | 预计用时: 30分钟 | 创建: 2026-08-12

📖 概述

日志是系统可观测性的基础，但没有规范的日志会导致两个极端：要么日志过多（Trace 级别全开，噪音淹没信号），要么过少（只有 Error 级别，出问题时无上下文）。更严重的是，如果 Domain 层直接调用框架的 LOG_* 宏，测试时无法断言日志输出——日志调用变成了不可测试的副作用。

本文档介绍一套 日志规范与分层策略：用六级日志（Trace→Fatal）定义每级的适用场景和内容约定，用 ILogger port 接口让 Domain 层通过抽象日志（可测试），用 FakeLogger 在测试中断言日志输出，Adapter 层可以直接用框架 LOG_* 宏。

2.1 六级日志分类

级别 适用场景 内容约定 示例
Trace 深度调试——函数参数/返回值、SQL 字符串、每次迭代细节 极度详细，生产从不开启 LOG_TRACE << "findOne: hash=" << hash
Debug 开发排障——变量值、分支决策、内部状态转储 中等详细，开发时开启 LOG_DEBUG << "Token validated, scopes=" << scopes
Info 关键流程检查点——启动/关闭、登录、任务完成 简洁但信息完整，生产开启 LOG_INFO << "User logged in: " << subject
Warn 可恢复的降级——默认值使用、资源接近阈值 说明问题和降级行为 LOG_WARN << "Redis unavailable, using memory fallback"
Error 单次操作/请求失败——服务仍可用 错误 + 上下文 + 请求 ID LOG_ERROR << "Token save failed: " << e.what()
Fatal 服务无法继续——必须罕见 极少使用，通常用 Error LOG_FATAL << "Config file missing"

使用原则：

  • 生产环境开 Info 级别，出问题时临时开 Debug/Trace
  • Error 是最常见的错误级别——单个请求失败不影响其他请求
  • Fatal 应极少使用——大多数”严重”错误其实是单个请求的 Error

*为什么 Domain 层用 ILogger 而非 LOG_ **：

  • 可测试性：测试时注入 FakeLogger，断言日志输出

4. 常见问题

Q: Domain 层用 ILogger 会不会有性能开销？

A: 虚函数分派开销在非热路径上可忽略。对于热路径（如每秒数千次调用的方法），可以在 ILogger 中加一个 bool isEnabled(LogLevel) 查询，在日志构造前检查级别——如果 Trace 级别未开启，不构造日志消息字符串。

Q: 为什么不在 Domain 层也直接用 LOG_ 宏？*

A: 两个原因。第一，可测试性——LOG_* 宏直接输出到 Drogon 日志系统，测试时无法捕获和断言。ILogger 是接口，测试时注入 FakeLogger 可以精确断言日志内容。第二，框架解耦——Domain 层是框架中立的 SDK 包，不应该依赖 Drogon 的日志宏。如果未来更换框架，Domain 层日志调用不需要改动。

Q: FakeLogger 的 entries_ 会不会无限增长？

A: 在测试中不会——测试用例执行时间短，日志条目有限。在生产中不会用 FakeLogger。如果担心内存，可以加一个 maxEntries 限制，超过后丢弃最旧的（环形缓冲区）。

📝 总结

关键要点:

  1. 六级日志：Trace（深度调试）→ Debug（开发排障）→ Info（关键流程）→ Warn（降级运行）→ Error（单次失败）→ Fatal（极少）
  2. Domain 层用 ILogger port：可测试（FakeLogger 断言）、框架解耦
  3. **Adapter 层直接用 LOG_***：Controller 依赖框架，不需要解耦
  4. 日志内容约定：包含上下文 + 请求 ID，敏感信息不落日志
  5. 生产开 Info，排障临时开 Debug/Trace

💡 提示: 日志规范的最高价值不在于”写了什么日志”——而在于”测试可以断言日志行为”。当 FakeLogger 让你能在测试中验证”客户端不存在时应该记录 Warn 级别日志”，日志就变成了可验证的行为约定，而非随意的副作用。
