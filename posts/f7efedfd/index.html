🔀 Feature Gating 条件编译模式

文档信息 | 难度: intermediate | 预计用时: 25分钟 | 创建: 2026-08-12

📖 概述

在 SDK 项目中，不是所有消费者都需要全部功能。一个认证 SDK 可能包含 OAuth2 核心、身份管理、社交登录、WebAuthn 等模块。某些消费者只需要 OAuth2 核心，不需要拉入社交登录的依赖。如果不提供条件编译，消费者被迫接受全部依赖面——增大构建时间、增加攻击面、引入不需要的传递依赖。

本文档介绍一种 Feature Gating 条件编译模式：用 CMake option() 定义功能开关，用 Conan 的 with_* options 作为消费者入口，通过 conanfile.py 的 generate() 方法将 Conan 选项透传到 CMake 缓存变量，用条件 add_subdirectory() 控制哪些模块参与编译。

🎯 学习目标

通过本文档，您将掌握：

  • CMake option 和 Conan option 的联动机制
  • conanfile.py 的 generate() 方法桥接两个构建系统
  • 条件 add_subdirectory() 的使用方式
  • 功能关闭时的依赖面缩减效果

这会：

  1. Conan 不解析 WebAuthn 的传递依赖（如 libcbor）
  2. generate() 将 WITH_WEBAUTHN=False 写入 conan_toolchain.cmake
  3. CMake option(WITH_WEBAUTHN) 读取为 OFF
  4. if(WITH_WEBAUTHN) 为假，不 add_subdirectory(libs/identity/webauthn)
  5. 最终产物不包含 WebAuthn 代码和依赖

4. 最佳实践

4.1 默认 ON 保持兼容

默认 ON 确保现有消费者的构建行为不变。只有明确要求缩减依赖面的消费者才主动关闭选项。

4.2 死依赖主动移除

功能门控的依赖也应该条件化——with_webauthn=False 时不应解析 libcbor 依赖。当功能尚未真正实现时，即使 with_webauthn=True 也不应保留虚假依赖。

4.3 选项层级关系

子功能依赖父功能——不能只启用社交登录而不启用身份管理。这种层级关系应该在 CMake 配置期强制检查。

5. 常见问题

Q: 为什么不用 C++ 预处理器（#ifdef）直接门控，还要 CMake option？

A: 两者配合使用。CMake option 控制 (1) 哪些源文件参与编译 (add_subdirectory/target_sources) 和 (2) 哪些依赖被拉入。C++ #ifdef 控制编译期代码路径。如果只用 #ifdef 而不用 CMake option，源文件仍会编译（浪费），依赖仍会拉入（浪费）。

Q: Conan option 和 CMake option 能否不一致？

A: 技术上可以（手动设置不同值），但 generate() 方法的 tc.variables 会用 Conan 的值覆盖 CMake 的默认值。所以消费者通过 Conan 设置的选项会正确传递到 CMake。直接用 cmake -DWITH_WEBAUTHN=OFF 也可以绕过 Conan，但两种入口应该保持一致。

📝 总结

关键要点:

  1. 三步联动：Conan option → generate() 透传 → CMake option → 条件 add_subdirectory
  2. 默认 ON：保持现有行为，消费者主动关闭不需要的功能
  3. 依赖面缩减：关闭的功能不编译源文件、不拉入传递依赖
  4. 层级关系：子功能依赖父功能，CMake 配置期强制检查

💡 提示: Feature Gating 的核心价值不在于”能关掉功能”——而在于”让消费者为依赖面付费时做出明确选择”。默认全开让现有消费者无感，需要缩减的消费者用一行 -o with_xxx=False 就能精简构建。
