📦 发布与供应链安全模式

文档信息 | 难度: intermediate | 预计用时: 30分钟 | 创建: 2026-08-12

📖 概述

软件发布是供应链安全的关键环节——如果发布产物被篡改，下游所有消费者都受影响。近年来供应链攻击（如 SolarWinds 事件）表明，即使源码安全，发布过程中的中间人攻击、镜像仓库被入侵、构建机器被入侵等都可能导致消费者拿到被篡改的产物。

本文档介绍一套 发布与供应链安全模式：用 SemVer 标签触发发布流程，生成多架构容器镜像（amd64 + arm64），用 cosign keyless 签名镜像（基于 GitHub OIDC，无需管理密钥），用 syft 生成 SPDX SBOM，用 SHA-256 校验和守护 SDK tarball 完整性。每个产物都有可验证的签名和物料清单。

2.1 SemVer 标签驱动发布

SemVer 约定：

版本格式 含义 例子
v1.0.0 首次正式发布 功能完整
v1.1.0 新增功能（向后兼容） 新增 WebAuthn 支持
v1.1.1 修复（向后兼容） 修复 token 验证 bug
v2.0.0 破坏性变更 API 不兼容重构

只有 v*.*.* 格式的标签触发发布——这防止 v1.0.0-beta 或 latest 等非 SemVer 标签意外触发。

2.5 SPDX SBOM 生成

SBOM 的用途：

许可证审计 检查依赖的许可证是否符合项目要求

3.2 权限最小化

GitHub Actions 的 permissions 字段应该精确授予需要的权限，不使用 permissions: write-all。

3.3 缓存策略

type=gha 使用 GitHub Actions 缓存。mode=max 缓存所有层（包括中间层），最大化缓存命中率。首次构建几分钟 → 后续构建秒级（只重新构建变更层）。

4. 常见问题

Q: cosign keyless 签名和传统密钥签名哪个更安全？

A: Keyless 签名不比传统密钥签名”更安全”——它解决的是密钥管理问题。传统密钥签名的安全性完全取决于密钥的保管——密钥泄露任何人都能签名。Keyless 签名不需要保管密钥，签名身份绑定到 GitHub OIDC token（仓库 + 工作流 + tag），只有该仓库的 CI 能产生该签名。

Q: SBOM 为什么用 SPDX 格式而非 CycloneDX？

A: 两者都是 SBOM 标准格式。SPDX 是 ISO 标准（ISO/IEC 5962），在工业和政府领域更广泛接受。CycloneDX 更专注于安全用例。选择取决于消费者需求——如果面向政府/企业客户，SPDX 更合适。

Q: 多架构镜像会增大存储吗？

A: 是的，但比维护两个单架构镜像仓库更方便。多架构镜像是一个 manifest list，指向两个架构的单架构镜像层。存储约为单架构的 2 倍，但消费者只需 docker pull 一次，自动选择匹配架构。

📝 总结

关键要点:

  1. SemVer 标签驱动：只有 v*.*.* 标签触发发布流程
  2. 多架构镜像：QEMU + Buildx 构建 amd64 + arm64
  3. Cosign keyless：用 GitHub OIDC 签名，无需管理密钥，身份绑定到仓库
  4. SPDX SBOM：用 syft 生成，用 grype 扫描漏洞
  5. SDK 校验和：SHA-256 校验和文件，消费者验证完整性
  6. 权限最小化：permissions 精确授权，不用 write-all

💡 提示: 供应链安全的核心价值不在于”防止所有攻击”——而在于”让篡改可检测”。即使攻击者入侵了镜像仓库，cosign 签名验证会失败；即使篡改了 SDK tarball，SHA-256 校验和不匹配。可验证性是供应链安全的基石。
