📡 可观测性模式：指标、审计与健康检查

文档信息 | 难度: intermediate | 预计用时: 30分钟 | 创建: 2026-08-12

📖 概述

系统可观测性由三大支柱构成：指标（metrics）、日志（logs）和追踪（traces）。在 C++ Web 服务中，实现可观测性需要：将运行时指标导出给 Prometheus、将安全事件记录为结构化审计日志、提供分层健康检查端点让负载均衡器和编排系统判断服务状态。

本文档介绍一套 可观测性模式设计：用 IMetrics port 接口让 Domain 层报告指标（可测试），用 IAuditSink port 接口记录审计事件，用分层健康检查（/health/live 和 /health/ready）区分进程存活和依赖可用。所有 port 接口都有 Fake 实现用于测试。

🎯 学习目标

通过本文档，您将掌握：

  • IMetrics port 接口设计和 Counter/Gauge/Histogram 模式
  • IAuditSink 审计事件的结构化记录方式
  • 分层健康检查（live vs ready）的设计原理
  • Domain 层可观测性 port 的可测试性

3. 最佳实践

3.1 指标命名规范

示例：

  • token_requests_total — token 请求计数
  • token_generation_duration_ms — token 生成延迟（毫秒）
  • db_connections_active — 活跃 DB 连接数

3.2 标签设计

标签的值集合应该有界且小（< 10 种）。高基数标签（如 user_id）会导致 Prometheus 存储爆炸——每个标签组合都是独立的时间序列。

3.3 审计日志的不可变性

审计日志应该追加写入，不可修改或删除。在数据库中，审计表不应有 UPDATE/DELETE 权限。在文件系统中，审计日志文件应设为追加模式。

4. 常见问题

Q: 为什么用 IMetrics port 而非直接用 Prometheus 客户端库？

A: 同样的原因——可测试性和解耦。Domain 层通过 IMetrics 报告指标，测试时注入 FakeMetrics 断言指标调用。生产时注入 PrometheusMetrics 实现。如果未来更换指标系统（如 StatsD），只需更换实现。

Q: 健康检查的 SELECT 1 会不会给数据库造成负担？

A: SELECT 1 是最轻量的 SQL 查询——不访问任何表，只验证连接是否存活。合理频率（如每 10 秒一次）不会对数据库造成可测量的负担。这是 connectivity probe 的标准做法。

Q: 审计日志和操作日志有什么区别？

A: 操作日志记录系统运行状态（INFO/DEBUG/WARN/ERROR），面向开发运维。审计日志记录安全相关事件（登录、Token 签发、权限变更），面向合规和安全审查。审计日志通常有更严格的保留要求（如 90 天或更长）且不可修改。

📝 总结

关键要点:

  1. 三大支柱：指标（Prometheus /metrics）、审计日志（IAuditSink）、健康检查（/health/live + /health/ready）
  2. Domain 层 port 抽象：IMetrics 和 IAuditSink 让 Domain 层可观测性可测试
  3. live vs ready：live 检查进程存活（重启），ready 检查依赖可用（移出负载均衡）
  4. 低基数标签：标签值集合有界且小，防止 Prometheus 存储爆炸
  5. 审计日志不可变：追加写入，不可修改删除，面向合规审查

💡 提示: 可观测性的核心价值不在于”能看到数据”——而在于”能在出问题时快速定位”。指标告诉你”什么出了问题”（如 token 生成延迟升高），审计日志告诉你”谁做了什么”（如某客户端的异常 token 请求），健康检查告诉你”服务是否可用”。三者配合构成完整的故障诊断链路。
