🚀 CI Pipeline 三关卡快速失败设计

文档信息 | 难度: intermediate | 预计用时: 35分钟 | 创建: 2026-08-12

📖 概述

在大型 C++ 项目中，CI pipeline 的构建和测试时间可能很长（数十分钟）。如果所有检查都在一个 job 中串行执行，开发者需要等待很长时间才能发现问题——反馈周期过长。

本文档介绍一种 三关卡快速失败（Three-Gate Fail-Fast）CI pipeline 设计：将 CI 拆分为 FAST、MAIN、RELEASE 三个关卡，每个关卡有不同的验证范围和速度。FAST 关卡只做源码级检查（秒级），失败立即阻断后续；MAIN 关卡做完整构建矩阵（分钟级）；RELEASE 关卡验证 SDK 打包。这种设计确保最便宜的检查最先运行，最贵的检查只在前置关卡通过后执行。

🎯 学习目标

通过本文档，您将掌握：

  • 三关卡 pipeline 的分层原理和关卡间依赖关系
  • FAST 关卡的设计：架构守护、迁移检查、命名验证、API diff
  • MAIN 关卡的构建矩阵设计：三平台 × 多编译器
  • RELEASE 关卡的 SDK 消费者验证
  • fail-fast 策略在 CI 中的应用

1. 基础概念

2. 实现原理

2.1 FAST Gate — 源码级检查（秒级）

FAST gate 不编译任何代码，只做静态分析和文件检查。它的设计目标是秒级完成，在开发者提交后立即反馈。

FAST gate 包含的检查项：

检查 工具 速度 目的
架构守护 arch_guard.py ~2s Domain 层不引用 Drogon/ORM
迁移检查 migration_check.py ~2s 命名规范、幂等性、校验和不变性
测试命名 naming_validator.sh ~1s {Category}_{Priority}_{Module}_... 格式
脚本一致性 manage-parity-check.sh ~1s manage.sh 和 manage.ps1 命令一致
OpenAPI 验证 redocly ~5s API 规范文件语法正确
前端属性测试 Vitest ~30s 前端快速门控

2.2 MAIN Gate — 构建矩阵（分钟级）

MAIN gate 在 FAST gate 通过后运行，执行完整的编译、单元测试和集成测试。使用构建矩阵在三个平台并行运行。

MAIN gate 矩阵设计：

平台 编译器 存储后端 特殊配置
Linux GCC PostgreSQL + Redis 完整集成测试
Windows MSVC 仅内存存储 -DOAUTH2_MEMORY_TESTS_ONLY=ON
macOS Clang ARM64 无 DB 仅构建验证

平台差异的原因：

  • Linux 做完整集成测试：PostgreSQL 和 Redis 在 Linux CI 上最容易配置，且 GCC 是 Drogon 的主要目标编译器
  • Windows 用内存存储：Windows CI 上配置 PostgreSQL/Redis 复杂且不稳定。内存存储后端支持与真实后端相同的接口契约，通过 -DOAUTH2_MEMORY_TESTS_ONLY=ON 跳过 DB 依赖测试
  • macOS 仅构建验证：确保代码在 Apple Silicon 上编译通过，不运行完整测试（节省 CI 时间）

2.3 RELEASE Gate — SDK 消费者验证

RELEASE gate 验证 SDK 可以被外部消费者通过 find_package() 正确消费。

3. 最佳实践

3.1 fail-fast 策略

fail-fast: true 确保当一个平台失败时，其他正在运行的平台被取消。这节省了 CI 资源——如果 Linux 构建已经失败，继续等待 Windows 和 macOS 构建完成没有意义。

3.2 关卡间依赖

关卡间用 needs 建立依赖关系。FAST gate 失败时，MAIN gate 和 RELEASE gate 自动跳过。这确保最贵的检查只在前置关卡通过后执行。

3.3 超时设置

超时设置防止 CI 挂起浪费资源。每个关卡有合理的超时上限——如果超过，说明有环境问题或代码问题需要调查。

3.4 WERROR 在 CI 中开启

本地开发时 AUTHFORGE_WERROR=OFF（不阻断），CI 中 ON（强制零警告）。这平衡了开发体验和代码质量。

4. 常见问题

Q: 为什么不在一个 job 中串行执行所有检查？

A: 串行执行意味着如果第一个检查失败，后面的检查不会运行——开发者不知道后面是否还有问题。三关卡设计中，FAST gate 的多个检查项可以并行执行，失败时开发者一次看到所有 FAST gate 检查的结果（通过/失败/跳过），不需要多轮提交来逐个发现。

Q: 为什么 Windows 不运行完整集成测试？

A: 在 Windows CI 上配置 PostgreSQL 和 Redis 需要额外的服务容器或 Chocolatey 安装，增加 CI 复杂度和不稳定性。内存存储后端实现了与 PostgreSQL/Redis 相同的 Repository 接口，契约测试套件确保接口行为一致。因此 Windows 上运行内存存储的测试已经覆盖了业务逻辑，仅缺少 DB 特定行为（如事务原子性）。

Q: 如何处理 CI 缓存？

A: 使用 actions/cache 缓存 Conan 依赖和 CMake 构建目录。Conan 缓存路径 ~/.conan2 可以跨运行持久化，首次安装几分钟 → 后续几秒。CMake 构建目录可以增量编译，但需要注意 CMake 配置变更时需要清缓存。

📝 总结

关键要点:

  1. 三关卡分层：FAST（秒级，源码检查）→ MAIN（分钟级，构建矩阵）→ RELEASE（分钟级，SDK 验证）
  2. fail-fast 策略：最便宜的检查最先运行，失败立即阻断后续关卡
  3. 构建矩阵差异：Linux 做完整集成测试，Windows 用内存存储，macOS 仅构建验证
  4. CI 开启 WERROR：本地 OFF 不阻断，CI ON 强制零警告

💡 提示: 三关卡设计的核心思想是”渐进验证”——每个关卡的验证成本递增，但只在前置关卡通过后执行。这种”漏斗”模式最大限度地减少了 CI 资源浪费，同时给开发者最快的反馈。
