🌐 Web API 错误系统设计

文档信息 | 难度: advanced | 预计用时: 40分钟 | 创建: 2026-08-12

📖 概述

在 Web API 中，错误响应的设计直接影响客户端的体验和调试效率。返回裸 HTTP 状态码（如 401、500）让客户端不知道具体发生了什么；返回自由文本错误消息无法程序化处理；错误码散落在代码各处容易漂移和不一致。

本文档介绍一种完整的 Web API 错误系统设计：用 ErrorCatalog 作为错误码的编译期单一来源（包含应用错误码和 OAuth2 协议错误码），用 Error 结构体携带稳定字符串码（如 AUTH_INVALID_CREDENTIALS）、数值码（如 4001）、类别、HTTP 状态码和客户端安全消息，用 ErrorContext 控制生产/开发模式下错误详情的暴露程度。还包含错误目录不变量自验证、API 文档与目录一致性测试。

🎯 学习目标

通过本文档，您将掌握：

  • 错误目录（ErrorCatalog）的编译期静态表设计和不变量验证
  • 稳定字符串码 + 数值码的双轨编码方案
  • 数值码分段（segment）按类别隔离的设计
  • ErrorContext 控制错误详情暴露的安全策略
  • OAuth2 协议错误码（RFC 6749 §5.2）的集成方式

3. 最佳实践

3.1 错误码稳定性

稳定字符串码一旦发布就不应该改变——客户端可能依赖它做条件处理。数值码同样稳定。如果需要废弃一个错误码，标记为 deprecated 但不要删除或重用。

3.2 details 的安全边界

details 可能包含敏感信息（SQL 语句、内部路径、堆栈跟踪）。在生产模式下暴露这些信息是安全漏洞——攻击者可以利用内部信息进行更精准的攻击。

4. 常见问题

Q: 为什么同时有字符串码和数值码？

A: 字符串码对人类可读（日志、文档、客户端代码中直接引用），数值码对机器高效（数据库索引、指标标签、协议传输）。双轨编码让两种消费者都能以最适合自己的方式引用错误。数值码的分段设计还让从数值码反查类别成为可能——一个 4xxx 错误一定是 AUTHENTICATION 类别。

Q: 为什么不用 enum 代替字符串码？

A: enum 的值在编译后不可变（无法从配置或数据库加载），跨语言/跨进程传递需要序列化，且 enum 名称变更需要重新编译所有消费者。字符串码天然可序列化、跨语言兼容、可动态加载。

Q: validateInvariants 什么时候运行？

A: 在测试中运行——通常在 ErrorCatalogTest 中调用 validateInvariants()，如果不变量被违反，测试失败。这确保新增错误码时（开发者向 catalog 添加条目），数值码分段、唯一性、HTTP 状态范围等约束自动验证。在 Domain 层抛 std::logic_error 而非用 LOG_FATAL/abort()——因为 Domain 层不应该依赖框架的日志系统。

📝 总结

关键要点:

  1. ErrorCatalog 编译期静态表：错误码、数值码、HTTP 状态、默认消息的唯一来源
  2. 双轨编码：稳定字符串码（人类可读）+ 数值码（机器高效），数值码按类别分段
  3. ErrorContext 安全模式：生产模式不暴露 details，开发模式暴露帮助调试
  4. 不变量自验证：编译期静态表在测试时验证唯一性、分段、HTTP 范围等约束
  5. OAuth2 协议错误码：RFC 6749 §5.2 的 13 个标准错误码集成到统一目录

💡 提示: 错误系统的核心价值不在于”返回了错误”——而在于让错误成为 API 契约的一部分。客户端可以依赖稳定错误码做条件处理（如 4001 重试登录、3012 等待后重试），这比解析 HTTP 状态码或匹配自由文本消息可靠得多。
