📦 CMake SDK 打包模式

文档信息 | 难度: advanced | 预计用时: 40分钟 | 创建: 2026-08-12

📖 概述

当一个 C++ 项目需要作为 SDK 被其他项目通过 find_package() 消费时，标准的 install(EXPORT) 只生成 install-tree 的 package config。这意味着消费者必须先 cmake --install 才能使用 SDK——对于 CI 中的 smoke test 或开发时的快速验证，这个安装步骤是不必要的摩擦。

本文档介绍一种 双套 CMake package config 模式：用 authforge_package() 函数同时生成 install-tree 和 build-tree 两套 package config，让消费者可以通过 CMAKE_PREFIX_PATH 指向 build 目录就能 find_package() 消费整个 SDK，无需安装步骤。同时处理 EXPORT_NAME 别名、find_dependency() 传递闭包和版本兼容性文件。

🎯 学习目标

通过本文档，您将掌握：

  • install-tree 和 build-tree 双套 package config 的生成方式
  • EXPORT_NAME 解决导出目标命名问题
  • find_dependency() 闭包确保传递依赖自动解析
  • configure_package_config_file() 的模板和路径处理
  • build-tree export 在 SDK smoke test 中的应用

2.1 问题：标准 install(EXPORT) 的三个缺陷

缺陷 后果
文件名与内容不匹配 Config.cmake 应该有 @PACKAGE_INIT@ 和 find_dependency()，但 install(EXPORT) 只生成 target 定义
无 find_dependency() 闭包 消费者 find_package 后，传递依赖（如 jsoncpp）不会被自动解析，链接失败
无 EXPORT_NAME 设置 导出目标名变成 authforge::authforge-common 而非 authforge::common
只有 install-tree 消费者必须先安装才能使用

2.2 解决方案：authforge_package() 函数

2.3 Config 模板文件

模板的关键点：

  • @PACKAGE_INIT@ 展开为路径修正代码，让 PACKAGE_PREFIX_DIR 指向正确的安装/build 目录
  • @AUTHFORGE_FIND_DEPENDENCY_BLOCK@ 展开为一系列 find_dependency(xxx) 调用，确保传递依赖被解析
  • include(...Targets.cmake) 导入实际的 target 定义

4. 最佳实践

4.1 EXPORT_NAME 与 ALIAS 的一致性

in-tree 代码用 authforge::common（ALIAS），外部消费者也用 authforge::common（EXPORT_NAME）。两者一致——同一代码可以用 ALIAS 在 in-tree 消费，也可以用 find_package 在 out-of-tree 消费，无需改代码。

4.2 传递依赖闭包的完整性

DEPENDENCIES 列表必须完整——遗漏任何一个传递依赖，消费者 find_package 后链接时会报 undefined reference。这里的”完整”指 PUBLIC 和 INTERFACE 链接的依赖（PRIVATE 链接的依赖不需要，因为它们已经静态链接到 STATIC 库中）。

4.3 SameMajorVersion 兼容性

SameMajorVersion 表示 1.x.x 版本的 SDK 与 1.0.0 的 ConfigVersion 兼容。消费者请求 find_package(authforge-common 1.0) 会匹配任何 1.x.x 版本。这符合 SemVer 的向后兼容承诺。

5. 常见问题

Q: build-tree export 和 install-tree export 的 Config 文件有什么区别？

A: 路径不同。install-tree 的 PACKAGE_PREFIX_DIR 指向安装目录（如 /usr/local），build-tree 的指向 build 目录（如 build/authforge-cmake/authforge-common）。configure_package_config_file() 用 INSTALL_PREFIX 参数区分这两种场景。

Q: 为什么用 include_guard(GLOBAL) 而不是普通的 include guard？

A: include_guard(GLOBAL) 确保这个模块在整个 CMake 配置过程中只 include 一次。多个包都调用 authforge_package()，如果每次都重新 include 会重复定义 AUTHFORGE_BUILD_CMAKE_DIR 等变量。CACHE INTERNAL 也辅助实现这一点。

Q: 消费者如何知道需要哪些传递依赖？

A: 不需要知道——这就是 find_dependency() 闭包的价值。Config 模板中的 find_dependency() 调用会自动解析所有传递依赖。消费者只需 find_package(authforge-drogon)，Config 文件会递归地 find_dependency 所有需要的包。

📝 总结

关键要点:

  1. 双套 package config：install-tree（安装后消费）+ build-tree（无需安装直接消费）
  2. EXPORT_NAME：设置 authforge::common 而非 authforge::authforge-common
  3. find_dependency() 闭包：Config 模板自动解析传递依赖
  4. SameMajorVersion：符合 SemVer 的版本兼容性策略
  5. build-tree → CI smoke test：ctest --build-and-test 验证真实消费者路径

💡 提示: build-tree export 的最大价值是让 CI 能在 SDK 构建后立即验证”外部消费者能否正确 find_package”——不需要安装步骤，直接指向 build 目录即可。这把 SDK 集成测试从”需要特殊环境”变成了”CI 标准步骤”。
