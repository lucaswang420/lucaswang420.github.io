📋 数据库迁移管理规范

文档信息 | 难度: intermediate | 预计用时: 30分钟 | 创建: 2026-08-12

📖 概述

在数据库驱动的项目中，schema 变更通过 SQL 迁移文件管理。没有规范的迁移管理会导致命名混乱（v1.sql、add_users_table.sql、2024-01-15-update.sql 混杂）、已应用的迁移被修改（生产环境与代码不一致）、迁移不可幂等（重复执行出错）等问题。

本文档介绍一套完整的 数据库迁移管理规范：用零填充连续命名（V001__*.sql 到 V022__*.sql）保证执行顺序和可排序性，用 CI 迁移守护工具检查命名规范、幂等性和已应用迁移的校验和不可变性。这套规范不依赖特定的迁移框架（如 Flyway、Liquibase），而是通过工具脚本在 CI 中强制执行。

🎯 学习目标

通过本文档，您将掌握：

  • 迁移文件命名规范和排序原理
  • 幂等性检查的实现方式
  • 校验和不可变性防止已应用迁移被篡改
  • CI 迁移守护工具的设计

2.1 命名规范

要素 规则 示例
前缀 大写 V V
序号 3 位零填充 001、022
分隔符 双下划线 __ __
描述 小写下划线 create_users_table
扩展名 .sql .sql

**为什么用双下划线 __**：Flyway 等迁移工具使用 V<version>__<description>.sql 格式，双下划线分隔版本号和描述。即使不使用 Flyway，这个格式也清晰地区分了序号和描述。

为什么用 3 位零填充：V001 到 V999 支持 999 个迁移。零填充确保字符串排序与数字排序一致——V001 < V002 < … < V022 < V099 < V100。没有零填充时 V1.sql < V10.sql < V2.sql（字符串排序）会导致错误顺序。

3. 最佳实践

3.1 新建迁移而非修改已有

修改已应用的迁移意味着生产环境的迁移日志（记录了哪个版本已执行）与文件内容不匹配。新建迁移始终是安全的——它从未执行过，不会与生产状态冲突。

3.2 迁移文件包含 DDL 和必要的 DML

种子数据作为迁移的一部分管理——不用单独的 seed 脚本。幂等的 INSERT 确保重复执行不报错。

3.3 迁移的回滚策略

不在迁移文件中写回滚逻辑——每个迁移只做正向变更。需要回滚时创建新迁移文件。这保持了迁移的单向性和不可变性。

4. 常见问题

Q: 校验和文件存在哪里？

A: 两种方案。方案一：存在代码仓库中（.migration_checksums 文件），与迁移文件一起提交。方案二：存在数据库的 migration_log 表中，记录每个已执行迁移的校验和。方案一更适合 CI 检查（不需要数据库连接），方案二更适合运行时检查。两者可以共存。

Q: 如果需要紧急修复生产 schema 怎么办？

A: 通过新迁移文件修复。即使生产只需要一个小修复（如添加索引），也创建 V023__add_urgent_index.sql。这保持了迁移历史的完整性和可审计性。直接用 psql 执行 SQL 而不创建迁移文件是反模式——生产 schema 变更不在版本控制中。

Q: 迁移检查会不会太严格？

A: 幂等性检查是建议性的（warning），校验和不变性是强制性的（error）。幂等性是最佳实践但有时 DDL 不支持 IF NOT EXISTS（如某些 PostgreSQL 版本的 ALTER TABLE），这些情况可以标注例外。校验和不变性是硬约束——修改已应用迁移是严重的安全风险。

📝 总结

关键要点:

  1. 零填充连续命名：V<NNN>__<description>.sql，确保排序和可识别性
  2. 幂等性保障：IF NOT EXISTS、条件检查、幂等 INSERT
  3. 校验和不可变性：已应用迁移不可修改，新建迁移做变更
  4. CI 三重检查：命名规范 → 幂等性 → 校验和不变性
  5. 单向迁移：每个迁移只做正向变更，回滚也是新迁移

💡 提示: 迁移管理的核心价值不在于”能执行 schema 变更”——而在于”让 schema 变更历史可审计、可重现、不可篡改”。当生产环境出问题时，迁移历史是最重要的调查线索。
