🎯 Result<T,E> 错误处理模式 (C++)

文档信息 | 难度: intermediate | 预计用时: 30分钟 | 创建: 2026-08-12

📖 概述

在 C++ 中，错误处理有三种常见方式：异常、返回码、和 optional/variant。异常适合跨层传播但控制流不透明；返回码简单但容易被忽略；std::optional 只能表达”有或无”但不能携带错误信息。

本文档介绍一种 Result<T,E> 模式：用 std::variant<T, E> 实现一个极简的成功-或-错误联合体，适用于 Domain 层同步方法的返回类型。它类似 Rust 的 Result 和 C++23 的 std::expected，但刻意保持极简——没有 monadic 组合子（map/and_then/or_else），避免投机性 API 膨胀。

决策 原因
std::variant<T, E> 存储 编译期确定大小，无堆分配，值语义
默认 E = Error 大多数场景用项目统一的 Error 类型，减少模板参数

无 monadic 组合子 刻意极简，避免投机性 API 膨胀；需要时用 if-else

4. 最佳实践

4.1 BadResultAccess 是编程错误

BadResultAccess 继承 std::logic_error——它代表的是编程错误（访问了错误的状态），而非运行时错误。与 std::optional::value() 在空状态下抛 bad_optional_access 的行为一致。

5. 常见问题

Q: 为什么不直接用 C++23 的 std::expected？

A: 项目可能需要支持 C++17（如 Drogon 框架的默认标准）。Result<T,E> 是 std::expected 的 C++17 替代品，接口刻意相似，未来迁移到 C++23 时可以平滑替换。

Q: 为什么 value() 抛异常而不是直接 UB？

A: 未检查就访问值是编程错误，但 UB（未定义行为）过于严厉——它可能导致任意不可预期的行为（数据损坏、安全漏洞）。抛 BadResultAccess 是安全失败——程序以可控方式终止，错误信息清晰。

Q: Result 有运行时开销吗？

A: std::variant 的运行时开销是一个 index 字段（1 byte 通常足够）和潜在的 padding。访问时有一个 branch（检查 index）。这些开销在非热路径上可忽略。对于热路径（如循环中的每次迭代），建议用 valueOr() 避免分支。

📝 总结

关键要点:

  1. 极简设计：std::variant<T, E> + 静态工厂 + value()/error() 抛异常，无 monadic 组合子
  2. 同步路径专用：Result 用于 Domain 层同步方法；异步方法用回调
  3. BadResultAccess = 编程错误：未检查就访问是 bug，用异常而非 UB 处理
  4. C++17 可用：是 std::expected 的 C++17 替代品，未来可平滑迁移

💡 提示: Result 类型的核心价值不在于”比异常更好”——而在于让错误成为类型系统的一部分。调用者必须处理错误路径才能访问值，这从类型层面消除了”忘记检查返回码”的问题。
